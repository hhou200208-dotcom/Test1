# Original BLA/LyaMAPPO reference for backbone comparison

This file freezes only **verified historical facts** needed to reproduce the
training protocol behind the existing BLA-MAPPO/LyaMAPPO convergence evidence.
It intentionally does not reinterpret the current paper equations.

## 1. Golden checkpoint anchor

Historical reference checkpoint:

- `checkpoints/LyaMAPPO_lh4_32K/`
- producing commit: `c5d8f909987c77d2a7abc708b9e62f4594c33eec`
- training budget: 32,000 physical slots = 500 rollouts/updates at 64 slots
- lambda_high: 4.0
- N = 25 (5 x 5)
- high-load fraction: 1/5
- V = 50
- ETA = 0.5
- PPO entropy beta = 0.02
- actor LR = 1e-4
- critic LR = 1e-3
- gamma = 0.99
- GAE lambda = 0.95
- PPO clip = 0.2
- minibatch = 64
- epochs = 2
- historical outcome-aware reward weights used for the golden checkpoint:
  `W_DONE=10, W_TIMEOUT=5, W_REJECT=5, W_HL=2, W_QUEUE=0.05`
- historical task-credit implementation: task reward z-score refinement with
  `BETA_TASK=0.5` (the historical LyaMAPPO implementation, not the later paper
  structured-cost equation with eta_c=0.1).

Authoritative historical command recorded by `checkpoints/README.md`:

```bash
python train_mappo_lambda4.py \
  --t_train 32000 --v 50 --beta 0.02 \
  --w_done 10 --w_hl 2 --w_timeout 5 --w_reject 5 \
  --n_runs 1 --tag lh4_32K
```

The checkpoint README also records non-negligible seed variance and warns that
an identical-hyperparameter retrain did not reproduce the exact golden scalar
metrics. Therefore the golden checkpoint must never be overwritten.

## 2. Existing BLA reward curve provenance

The paper/presentation convergence plot is generated by
`plot_reward_convergence.py` from an existing `reward_curve.json` containing
about 32,000 **per-slot** reward samples.

The plotting transformation is:

```python
K = 64
sx, sy = moving_average(per_slot_reward, window)
sy = sy * K
```

The standard figure uses a 700-slot moving average (about 11 rollouts); the
smoother figure uses 1600 slots (25 rollouts).  Thus the existing y-axis is a
smoothed **per-episode-magnitude** view derived from per-slot reward, not the raw
64-slot rollout-return CSV used by later backbone diagnostics.

Any new MAPPO/IPPO/MADDPG/QMIX training curve intended to share this figure must
be transformed with the same aggregation and smoothing convention.  Merely
multiplying an already aggregated return after the fact is not a sufficient
reproduction protocol.

## 3. Historical algorithm definition at the golden commit

The historical methodology committed at `c5d8f90` defines:

- 54-D shared Actor input and 5 discrete actions (local + 4 neighbors)
- 245-D scalable Critic input
- per-task sequential decision within a slot
- common Lyapunov/DVFS physical substrate
- outcome-aware reward augmentation
- task-level advantage refinement
  `A_task = A_slot + beta * (r_task - mean_slot) / std_slot`, `beta=0.5`

This is the implementation lineage that must be used if the existing BLA reward
curve is retained as a factual experimental result.

## 4. Important distinction from the current manuscript method

The current manuscript later formalizes a different, more explicit method:

- system reward `R_sys = (1/N) sum_n r_n^slot`
- lifetime coefficient `rho_L=10`
- structured task cost using queue differential + counterfactual marginal
  lifetime loss
- centered bounded task signal
- `eta_c=0.1`
- empirical lifetime normalization over an initial 100-slot calibration window
- episode boundaries do not reset the continuing physical system

Those equations are not identical to the historical golden implementation.
Therefore one of the following must be chosen before final paper submission:

1. **Historical-anchor comparison**: keep the existing BLA curve and train all
   new RL backbones under the verified historical implementation/protocol.
2. **Current-paper exact comparison**: implement the manuscript equations and
   retrain BLA plus every backbone; the old BLA reward curve cannot then be
   presented as if generated by that new implementation.

The present project goal is historical-anchor comparison because the existing
BLA reward curve is to be retained.

## 5. rho_L sensitivity provenance warning

A recoverable `docs/rho_l_sweep.json` is explicitly marked as reconstructed from
chat after original container loss; it states that raw series, learning curves,
training times, and checkpoints for that sweep were unrecoverable.  It should
not be used as the sole provenance source for the training implementation.

The golden 32K checkpoint + its recorded command + the existing reward-curve
file are stronger anchors.

## 6. Next acceptance sequence

Before any five-algorithm formal rerun:

1. Reconstruct a clean historical runner from commit `c5d8f90` without
   overwriting the golden checkpoint.
2. Run one BLA/LyaMAPPO seed as a reproduction diagnostic (8K first).
3. Save raw per-slot system reward, rollout return, PPO entropy, completion rate,
   energy, and lifetime loss.
4. Recreate the reward curve with the exact old plotting transform.
5. Only after the diagnostic shows learning improvement and a stable plateau,
   freeze the runner and train MAPPO, IPPO, MADDPG and adapted QMIX under the
   same environment/external reward/training budget.
6. Evaluate all frozen checkpoints under one identical final evaluation
   protocol before reporting delay, energy, lifetime loss and satisfaction.

Do not use `results/backbone_compare/unified_32k_seed0/` as paper evidence; it
remains diagnostic only.
